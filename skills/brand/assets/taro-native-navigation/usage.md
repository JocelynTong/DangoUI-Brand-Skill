# Taro native navigation integration

This is a pure geometry helper, with no page DOM, brand styles, runtime calls or framework dependencies. Copy the bound `safe-area.mjs` into the isolated host and import `nativeNavigationGeometry` at the actual navigation consumer, or reuse an equivalent existing host calculation and record why in `reused/adapted/limitations`. Do not add a second navigation system.

Before changing the target page, trace its existing `navStyle`, inline `:style`/style props, status-bar calculation, capsule measurement, loading skeleton and navigation handlers. Inspect page/app navigationStyle config and direct shared shell dependencies. Determine which layer owns the status bar and capsule clearance. A generated image header is composition input, not a reason to stack another native header on the existing one.

For a custom native navigation shell, pass actual Taro window metrics and getMenuButtonBoundingClientRect results to the helper. Coordinates and output are logical px: use px styles, not rpx or screenshot pixels. Use safeTop as the bottom of the complete native safe region, navigationHeight only as the row below the status bar, and rightInset to reserve capsule space for controls sharing that row. An immersive illustration may extend behind the safe region; interactive content must clear it. Do not add safeTop and statusBarHeight twice. A system-managed native navigation bar already owns its safe area; do not apply an extra custom-header inset.

If the selected header replaces the existing layout, detach or reconcile its old inline height/padding binding for that target branch; ordinary stylesheet declarations cannot reliably override inline geometry. Keep unchanged branches and loading states coherent. Preserve navigation events, real data, selected image bytes and single-page scope. Do not copy a repaired trial page.

Missing/invalid native metrics must be reported as unverified, not assigned invented device constants. Recompute from the host lifecycle when metrics change. The helper throws on invalid measurements so callers explicitly handle unavailable native runtime.

Implementation and independent QA must exercise the actual mini-program runtime (native simulator/devtools or device), inspect status-bar/capsule/header bounds, loading and loaded states, clipping, native menu clearance, taps and return navigation at target and narrow viewports. Record actual runtime/platform, metrics, consumer and screenshots in existing evidence/observations. H5, proxy-rendered pages and successful native compilation are supplemental evidence only; they cannot pass native navigation validation. If native runtime cannot be checked, report the blocker and keep nativeRuntime false. No new image generation or whole-host reskin is authorized.
