做一个页面时，依次拿三种“材料”

01 / DangoUI 组件

拿得到的零件

Search、Input、Tag、Button、Card。复用已有组件能力和语义，不在场景库复制另一份组件定义。

02 / 任务场景

把零件组织成任务

输入条件 → 调整筛选 → 看反馈 → 浏览真实结果。初始、加载、结果、无结果、失败，都有位置。

03 / 已学品牌

决定它长什么样

从冻结的品牌 token、素材和构图配方选择合适的表达；不得把素材颜色随意变成按钮或页面底色。

expressive 和 productive 各放哪里？

这不是规定“上面一张大图、下面一排列表”。它只规定任务要顺利完成，品牌表达要有来源。

进入任务 · EXPRESSIVE

可以建立探索氛围

允许品牌主题、资产、字体与空间关系组成第一眼场景，但必须把人自然带到搜索动作；不强制 Hero。

持续操作 · PRODUCTIVE

要快速找得到

搜索、筛选和反馈始终清楚可用。品牌可以进入控件的字体、形状和局部材质，不牺牲阅读或操作效率。

浏览结果 · BLENDED

真实内容与品牌共处

结果容器可有品牌构图机制；业务记录必须来自真实宿主，不能把活动图当结果，更不能编造卡组数据。

之前三份 H5 是一次实验，不是场景库推荐你照抄的三个版式。它们的机器检查曾通过，但你指出了实际审美问题。

旧方案 01 · ARENA SEARCH

有第一眼，但没有闭环

入口能看到一些 expressive 意图；仍需验证素材、token 和后续检索任务是否形成同一场景。

旧方案 02 · SEARCH CONSOLE

效率不能等于通用后台

任务结构清楚不代表品牌学会了。品牌机制若只剩点缀，不能当作 expressive 通过。

旧方案 03 · INDEX FIRST

换排列不等于换构图

列表顺序或容器变化不能充当真正不同的品牌场景；需要重新设计内容与品牌素材的关系。

上述是问题归纳，不是新的 QA 判决。三案尚未重新制作或获得你的审美认可。

这次脚本究竟帮什么忙？

Designer 必须写清“采用哪个场景、哪些组件和任务状态”；H5 必须找得到搜索、筛选、反馈、结果四个区域；用到 DangoUI 映射 token 时，值不能擅自漂移。脚本只能阻止可检查的错误，不能宣布画面惊艳。 下一次 design-host 仍要交付真实的三份 H5，由独立 QA 与你看效果。
